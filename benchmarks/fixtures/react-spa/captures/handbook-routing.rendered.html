Client routing and the canonical URL

Why a router that rewrites the canonical after mount leaves two different answers on record for the same URL.

The handbook shell hard-codes one canonical for the whole section. Somebody added it in good faith: before that edit the section had no canonical at all in its initial response, and a single hard-coded value looked like an improvement over nothing. It is an improvement for exactly one URL, the section root, and it is wrong for every article underneath it.

What a consumer records now depends on when it read the document. Fetch the URL without executing scripts and the answer is the section root, which asks the engine to fold every article into one page. Execute the scripts, wait for the effect, and the answer is the article's own URL, which is correct. Neither reading is unreasonable and the two disagree, so the site has published two conflicting identity claims for one document and cannot tell which one was believed.

The check that reports this does not assert which value wins, because that is not observable from the outside. It reports the divergence and names both values, which is the part a person can act on. The action is to stop treating the head as something the client owns: whatever produces the response - a build step, a server render, or an edge function - has to emit the article's canonical before the bytes leave, and the client then has nothing left to correct.

The same argument applies to the title and the description on this page, which also exist only after execution. The difference is that a missing title is visibly missing, while a wrong canonical looks like a correct one until somebody compares the two responses.
