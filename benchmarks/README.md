# Benchmarks

Fixture projects with planted defects, and the cases that say in advance what the
checks are supposed to conclude about each one.

The methodology — what a case declares, how each number is computed, and what a
score does and does not establish — is in [BENCHMARKS.md](../BENCHMARKS.md). This
file is the coverage register: which site types have a fixture, and which do not.

## Layout

```
benchmarks/
  cases/       one JSON file per case, validated against schema/benchmark-case.schema.json
  fixtures/    the project trees the cases point at
```

A fixture is a real directory tree — `package.json`, source files, `robots.txt`,
`sitemap.xml` — plus, where the case needs served bytes rather than source, a
`snapshot.json` and a `captures/` directory holding what each route actually
sends. Nothing is installed and nothing is built: a capture is authored HTML
representing the response, because the point of the exercise is to check that the
checks read served output rather than inferring it from `package.json`.

The table above is generated from what is on disk, so it cannot claim a fixture
that does not exist. That is deliberate — coverage is the easiest thing in a
repository like this to overstate, because an uncovered site type looks identical
to a covered one from the requirement registry alone: both have requirements,
both have sources, both have verification methods. Only a fixture shows whether
the applicability logic behaves on a realistic project of that shape.

## Reading a row

**`covered — X found / Y silent`** means the case ran and was scored: `X` findings
matched an expectation and `Y` checks ran, inspected the fixture, and correctly
reported nothing. `Y` is the number worth attention. A fixture that only proves
findings proves half of what matters; the checks that stayed quiet are the
evidence that an autonomous agent turned loose on the project would not have
modified working code.

**`no fixture`** means the requirements for that site type exist and are specified
— they carry sources, applicability conditions, and verification methods — and
nothing measures them. They are not known to be broken. They are unmeasured, and
those are different claims.

## Three statuses that are not true negatives

A check can decline to reach a verdict, and the scorer keeps those out of every
rate rather than counting them either way:

- **`NEEDS_RUNTIME`** — the check needs served bytes and the fixture supplied
  none.
- **`NOT_APPLICABLE`** — the check ran and decided the fixture is outside its
  scope. The hreflang checks say this about a monolingual site; the review-markup
  checks say it about a site that publishes no ratings.
- **never invoked** — the requirement behind the check was not `APPLICABLE` on
  this profile, so the selector never offered it. `audit` and `bench` both filter
  checks this way, which means a check in this state is *absent* from the results
  rather than reporting a status.

The last one is the trap for case authors. Running the whole check suite by hand
against a fixture will produce a `PASS` for a check that the shipped `audit`
command would never call, and writing that `PASS` into
`expected_non_findings` records a true negative for a code path no user reaches.
The scorer prints such an entry as `not measured` instead of crediting it. If you
see that line, the fix is to delete the entry, not to argue with it — and then to
ask whether the applicability gate that withheld the requirement is right, because
that question is usually the more interesting one.

## Adding a fixture

1. Read [BENCHMARKS.md](../BENCHMARKS.md). The five authoring rules there are
   binding, and the first one — never derive an expectation from tool output — is
   what the whole exercise rests on.
2. Build the tree, plant defects a real project of that kind would plausibly ship.
3. Write `declared_defects` and `expected_findings` **from the fixture, before
   running anything**, with each declared defect naming its requirement id.
4. Run. Where the output disagrees with the prediction, one of the two is wrong;
   finding out which is the entire value of having written the prediction down
   first. If the check is wrong, report the bug and leave the fixture
   demonstrating it — a planted defect that no check detects belongs in
   `declared_defects`, stays out of `expected_findings`, and is recorded as a
   coverage gap in `notes`.
5. Add the row to `INTENDED_FIXTURES` in `tools/lib/docs.mjs` if the site type is
   not already there. A case outside that matrix is listed separately below the
   table rather than silently absorbed.

## Running

```bash
npm run bench
```

```bash
node tools/cli.ts bench --case react-spa,vite-static
```

`npm run bench` passes `--write` and records `reports/benchmarks.json`; every
other form writes nothing.
